The problem

A public benchmark is a leaked exam.
A private one is a promise.

A

Public sets leak

Test questions end up in training data. A high score can mean the model learned the skill, or that it saw the answers.

B

Private sets can't be checked

Keep the questions secret and the leak stops, but now the score is just someone's word. Nobody outside can audit it.

C

Sealed Bench does both

The set stays sealed. A random sample, drawn by the chain after the fact, is opened and verified by a contract. Lying gets expensive fast.

Each attempt is sent to the real contract's check_reveal view: a free, read-only call that runs every check a real reveal would. Nothing is written on-chain.

The math

Twenty draws.
Nowhere to hide.

If the owner misreports some entries, the chain's 20-of-100 sample has to miss every one of them for the lie to survive. Drag to change how many entries are misreported.

Per run, exact hypergeometric odds. This is not the probability the score is correct, and it says nothing about benchmark quality.

90.5%chance the sample catches it

Built on NEAR

The chain does the part
nobody should be trusted with.

TEE-signed inference

Models run inside Intel TDX + NVIDIA confidential VMs on NEAR AI Cloud. Every response is signed by a key that never leaves the enclave.

GET /v1/signature/{chat_id}
// signs, EIP-191 personal_sign:
"MODEL:" + sha256(request) + ":" + sha256(response)

On-chain ecrecover

The contract rebuilds the exact request bytes, hashes both sides and recovers the signer itself.

let pk = env::ecrecover(&hash, &sig[..64], v, false)?;
let addr = &env::keccak256_array(&pk)[12..];
require!(pinned.contains(addr));

Chain randomness, twice

random_seed sets each run's nonce and, after every run is committed, draws the shared sample. Anyone can call the draw.

Attested signers

Each signer is pinned only after its TDX quote verifies with dcap-qvl. The report's sha256 is stored on-chain with the pin.

Free verification

The check_reveal view runs every check for free over RPC. This page uses it, and so can you.

Threat model

What you trust, what it proves,
and what it doesn't.

You trust

  • NEAR AI Cloud's TEE signing key for each model.
  • The admin who pins a signer after verifying its attestation off-chain (DCAP quote, report-data binding, MRCONFIGID, RTMR3 replay).
  • The model id, which is the gateway's claim, not proof of which weights ran.
  • Shared keys: instances of one model share a signer, so a match doesn't name the serving instance.

It proves

  • Revealed items were fixed before the run.
  • Each revealed response was produced for this run's nonce and signed by the pinned TEE key.
  • Committed grades match a deterministic re-grade of the raw bytes.
  • The score is the sum of the committed grade vector.

It doesn't prove

  • Unsampled entries. Checked only probabilistically, under the bound above.
  • Re-rolls. An owner could query many times and keep the best. Temperature 0 and the per-run nonce reduce this; they don't prevent it.
  • Secrecy from the owner. The set is hidden from vendors and the public, not from its owner.
  • Perfect randomness. Block producers can slightly bias random_seed. Production would use commit-reveal or a VRF.

Also: each reveal spends 20 items of the sealed set. The bond is a nominal 0.1 NEAR on testnet; slashing is out of scope. The DEV-ONLY mock signer uses a public key, is labeled mock/DEV-ONLY-not-a-TEE, and no claim cites it.

Verify it yourself
in 60 seconds.

No NEAR account, no wallet, no API key. Node 22.18+ and network access to testnet RPC.

  1. Replay the real audits. Re-derives the challenge from the chain seed, replays every reveal offline, then checks roots, grades, signers and check_reveal on-chain.
  2. Try to cheat. Nine lies against a real TEE-signed entry. All nine rejected, each with the contract's own reason.
  3. Check the TEE. Verifies NEAR AI's Intel TDX attestation for the pinned signer.
