Audit a private benchmark score by opening 20 of 100 entries.

The owner commits a Merkle root of a private test set, then each graded run, to a NEAR contract. Any account can then call the draw, and random_seed picks 20 of 100 entries. Each one must match its commitment, carry a pinned NEAR AI TEE signature and re-grade the same, or the run fails.

Problem

Published test sets can end up in training data.

A

Public sets leak

Published benchmarks get scraped into training corpora. A high score can then come from memorized answers.

B

Private scores rest on trust

An unpublished set limits exposure. Outsiders then have only the reported number.

C

Sealed Bench

The set stays private. After the runs are committed, the owner must reveal a random 20 of 100 entries, and the contract checks each one.

Result

GSM8K: public problems vs. private variants

25 public GSM8K problems and 100 unpublished numeric variants, 4 per problem. NEAR AI's TEE saw the variants; the 20 drawn are now public. Temperature 0. Both models score near 100% on both sets, so this result says nothing about contamination. One public problem is 4 points, so a 2-point gap is below resolution.

Tamper lab

Edit a signed entry and submit it

Each submission calls the contract's free check_reveal view, which returns the first failed check.

Detection odds

How often a misreport is caught

With 10 bad entries out of 100, the draw catches the run 90.5% of the time. With 2, 36%. Across 10 suites at 10% misreporting, at least one gets through 63% of the time. These figures assume an unbiased draw and no retries.

Hypergeometric, per run, 20 distinct entries of 100. This is not the probability that the score is correct.

NEAR

What runs on NEAR

TEE-signed inference

NEAR AI Cloud runs models in Intel TDX and NVIDIA confidential VMs and signs each response with an enclave key. The signature covers the gateway's model id. It does not identify the weights.

GET /v1/signature/{chat_id}
// EIP-191 personal_sign over:
model_id + ":" + sha256(request) + ":" + sha256(response)

On-chain ecrecover

The contract rebuilds the request from the committed template and recovers the signer.

// contract/src/verify.rs
let pk = env::ecrecover(&hash, &sig[..64], v, false).ok_or("ecrecover failed")?;
let h = env::keccak256_array(&pk);
addr.copy_from_slice(&h[12..]);
// contract/src/lib.rs
let pinned = self.signers.get(&run.model).cloned().unwrap_or_default();
if !pinned.iter().any(|p| p.address == addr) {
    fail!("signature not from a pinned signer for {}", run.model);
}

random_seed

Sets each run's nonce at start_run and picks the sample at the draw.

Pinned signers

The admin pins a key after checking its TDX quote off-chain with dcap-qvl. The report hash is stored with it. The contract does not verify the quote.

check_reveal

Runs the reveal checks as a free view. The explorer and tamper lab use it.

Threat model

Trust assumptions and limits

You trust

  • NEAR AI Cloud to keep each signing key inside its enclave. The provider sees every sealed entry inside the TEE.
  • The operator. Owner and admin are the same operator here. The admin pins keys after an off-chain check of the DCAP quote, report data, MRCONFIGID and RTMR3. In v1 a key pinned after a run still counts, and pins cannot be revoked.
  • The gateway's model id. The signature does not identify the weights.
  • Shared keys. All instances of a model use one signer, so a match does not identify the serving instance.
  • The upgrade key. The operator holds a full-access key to the contract account and has redeployed with state kept. Until that key is removed, it can deploy code that changes stored results.

A passing audit shows

  • The revealed questions and answer keys were committed before the run.
  • Each revealed response used this run's nonce and was signed by a key pinned for that model.
  • For each revealed entry, the committed grade matches a deterministic re-grade of the raw response.
  • The score equals the sum of the committed grade vector.

It does not show

  • Unsampled entries. They stay unchecked. The odds above are the only coverage.
  • Re-rolls. The nonce binds signed responses to the run. Best-of-N within the run is still possible.
  • Small misreports. 2 bad entries are caught 36% of the time.
  • Abandoned runs and suite shopping. In v1 an owner can leave a bad run uncommitted, which blocks the draw, or commit one set to several suites and keep the one that passes.
  • Secrecy from the owner. The owner sees and grades the set.
  • An unbiased draw. Block producers can bias random_seed. Here the operator's admin account called the draw, and v1 lets the caller batch it with reveals and retry. The fix is in v2, not yet deployed.

Revealed entries are public and must be retired from the private set. The 0.1 NEAR bond is locked on failure, not slashed. The mock signer's key is public; mock runs are labeled mock/DEV-ONLY-not-a-TEE and no claim cites them.

Reproduce

Check it from a clean clone

Needs Node 22.18+ and testnet RPC. No account or key. About two minutes.

  1. npm run verify Replays each reveal offline and compares roots, the draw, grades and signers with contract views.
  2. npm run tamper Applies nine edits to a signed entry and prints why each is rejected. Some are checked by the contract view, some offline.
~/sealed-bench 
$ git clone %GITHUB%
$ cd sealed-bench && npm ci

$ npm run verify
# expect "ok": true and every check true

$ npm run tamper
# expect "9/9 lies rejected; honest reveal accepted=true"
